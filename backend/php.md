## 🟡 Номера разделов Laravel-лабы указаны непоследовательно
В Laravel-методичке **разделы** (теория) такие: 3 — Service Container, 6 — HTTP-слой, 7 — Auth.
А **сессии**: 4 — HTTP, 5 — Service Container.
В PHP-лабе Container называется то «раздел 5», то «раздел 5.1», то «раздел 3». «Раздел 5» и «5.1» — это номера сессии и шага, а не раздела.

Уже совпадают: «раздел 3 (Container и провайдеры)» и «раздел 6 (middleware)».

## 📖 Вычитка методички

### Часть 1 (разделы 1–6.1)
- **[тех] Раздел 6.1, дерево иерархии Throwable** — «├── TypeError… ├── ValueError… ├── ArgumentCountError… └── DivisionByZeroError» (все четыре нарисованы как прямые потомки `Error` на одном уровне) → в реальности `ArgumentCountError extends TypeError` (не `Error` напрямую), а `DivisionByZeroError extends ArithmeticError extends Error` → поправить дерево: `ArgumentCountError` вложить под `TypeError`, `DivisionByZeroError` — под отдельную ветку `ArithmeticError`.

### Часть 2 (разделы 6.2–12)
- **[тех] (проверить) Раздел 6.2, порядок catch** — «catch (InvalidArgumentException $e) { // СПЕЦИФИЧНОЕ исключение — раньше, чем общее } catch (RuntimeException $e) {…}» → `InvalidArgumentException extends LogicException`, а `RuntimeException` — отдельная ветка от `LogicException`; они не в отношении «потомок/предок», поэтому порядок catch-блоков здесь на самом деле ни на что не влияет → либо убрать формулировку «специфичное раньше общего» (она подразумевает наследование, которого нет), либо взять пример с реальной иерархией (напр. `InvalidArgumentException` и `LogicException`).
- **[тех] (проверить) Раздел 9.2, тип `$resolvedInstance`** — «private static ?ArrayAccess $resolvedInstance = null; … self::$resolvedInstance ??= app('cache');» → нет причины типизировать резолвленный из контейнера сервис как `ArrayAccess` (реальный `Illuminate\Cache\Repository` этот интерфейс не реализует), тип выбран произвольно и не нужен для вызова `->$name(...$args)` → заменить на `?object` или убрать тип.

### Часть 3 (Сессия 1 — Сессия 3, шаг 3.3 начало)
- **[текст] Итог сессии 3** — «📖 Почитать: PHP: Exceptions — сессия 3 целиком про обработку ошибок.» → сессия 3 называется «Суперглобалы и обработка ошибок», из трёх шагов (3.1, 3.2) посвящены $_GET/JSON-телу запроса (суперглобалам), и только 3.3 — исключениям → неточно называть её «целиком про обработку ошибок»; поправить на «наполовину про обработку ошибок» или перечислить обе темы.

### Часть 4 (Сессия 3 конец — Сессия 6, шаг 6.1 начало)
- **[текст] Повторяющийся паттерн: «читать перед сессией» преувеличивает охват** — «📖 Почитать: PHP: References Explained — сессия 2 целиком про массивы и copy-on-write» (но шаг 2.3 — это mb_*/sprintf/regex, не массивы); «📖 Почитать: PHP: Reflection — сессия 6 целиком на нём» (но Reflection используется только в шаге 6.3, а 6.1–6.2 — ручное связывание и явные фабрики без Reflection) → убрать слово «целиком»/уточнить, что покрыта только часть сессии.

### Часть 5 (Шаг 6.2 — Шаг 7.4 начало)
- **[тех] Шаг 7.1, комментарий про PDO::ATTR_ERRMODE** — «PDO::ATTR_ERRMODE => PDO::ERRMODE_EXCEPTION, // без этого PDO молча игнорирует ошибки SQL!» и далее в «Зачем»: «без него… молча возвращает false вместо исключения» → неверно для целевой версии лабы: начиная с PHP 8.0 режим ошибок PDO по умолчанию уже PDO::ERRMODE_EXCEPTION (RFC «Saner PDO error mode default»), а не ERRMODE_SILENT — в PHP 8.4 эта опция ничего не меняет, ошибка и так бросит исключение → поправить формулировку («это уже поведение по умолчанию с PHP 8.0, опция здесь для явности») либо убрать как аргумент «зачем».
- **[противоречие] Шаг 7.1, имена файлов в коде vs в curl** — код подписан «// src/15_pdo_vulnerable.php» и «// src/16_pdo_safe.php», а команды дергают «localhost:8000/pdo-vulnerable.php» и «localhost:8000/pdo-safe.php» при `php -S 0.0.0.0:8000 -t public` → пути не совпадают: файлы с такими именами лежат в src/ и не будут отданы веб-сервером, поднятым над public/ (и по-другому названы: без префикса «15_»/«16_») → привести к одному имени и разместить оба файла в public/ (например public/pdo-vulnerable.php, public/pdo-safe.php).
- **[тех] Шаг 7.3, комментарий к session_start()** — «session_start(); // идемпотентно — если сессия уже стартовала, ничего не сломает» (вызывается и в token(), и в verify(), оба раза без проверки session_status()) → неточно: повторный вызов session_start() при уже активной сессии не «ничего не сломает» молча, а генерирует предупреждение «session_start(): Ignoring session_start() because a session is already active», которое при включённом display_errors попадёт в вывод раньше header('Content-Type: application/json') и может испортить JSON-ответ → обернуть в `if (session_status() === PHP_SESSION_NONE) session_start();` либо явно упомянуть предупреждение.
- **[тех] (проверить) Шаг 6.3, Container v2, метод build()** — «if (is_callable($concrete) && !is_string($concrete)) return $concrete($c);» при сигнатуре `string|callable $concrete` → раз concrete — строка, `!is_string($concrete)` всегда false, поэтому строковый callable (например, `"SomeClass::factory"` или имя глобальной функции) никогда не будет вызван как callable — код провалится в `new \ReflectionClass($concrete)` и бросит ReflectionException, а не вызовет функцию → в примерах методички это не проявляется (используются только имена классов и настоящие Closure), но комментарий/тип обещают больше, чем код умеет; либо сузить тип до `string`, либо поправить проверку.

### Часть 6 (Шаг 7.4 конец — Сессия 8, раздел 14, раздел 15 начало)
- **[тех] Шаг 8.1, код OrderController.php без открывающего тега** — единый блок кода подряд содержит «<?php declare(strict_types=1); // src/Controllers/MenuController.php … final class MenuController {…} // src/Controllers/OrderController.php namespace App\Controllers; final class OrderController {…}» → если скопировать вторую часть как отдельный файл src/Controllers/OrderController.php буквально (как подписано в комментарии), в нём не будет собственного `<?php declare(strict_types=1);` — PHP не распарсит файл как код (весь текст уйдёт в вывод как HTML) → добавить недостающий `<?php declare(strict_types=1);` перед `namespace App\Controllers;` для OrderController.php.
- **[тех] Шаг 8.3, код ContainerTest.php без открывающего тега** — тот же паттерн: «… final class RouterTest extends TestCase {…} // tests/ContainerTest.php use App\Container\Container; final class ContainerTest extends TestCase {…}» в одном блоке кода → при разнесении по файлам, как подписано, tests/ContainerTest.php останется без своего `<?php declare(strict_types=1);` → добавить тег для второго файла.
- **[противоречие] Раздел 14 (чек-лист) vs раздел 15 (глоссарий), TypeError и strict_types** — чек-лист: «strict_types, TypeError | 1.2: с strict_types и без, бок о бок | строгость файла, не глобальная настройка» (то есть в шаге 1.2 показано, что TypeError бывает и БЕЗ strict_types), а глоссарий: «TypeError — исключение (точнее, Error) при несовпадении типа аргумента/возврата под strict_types» → формулировка глоссария подразумевает, что TypeError возникает только при strict_types, что противоречит собственному шагу 1.2 этой же методички (TypeError бросается и без strict_types — например, при явно несовместимых типах или встроенных функциях) → уточнить: «…при несовпадении типа, особенно заметно под strict_types».

- **[тех] Шаг 1.1: `pdo_pgsql` не ставится, и ошибка проглочена.** `docker-php-ext-install pdo_pgsql >/dev/null 2>&1` падает с `Cannot find libpq-fe.h` (в `php:*-cli` нет `libpq-dev`), `sleep infinity` держит контейнер как будто всё хорошо, `php -m | grep pdo` показывает только `PDO`, `pdo_sqlite`. - **[тех] Шаги 7.1, 7.2, 8.1: `docker compose exec app psql …` — в контейнере `app` нет `psql`** (и пароль пришлось бы вводить). → `postgresql-client` в том же `apt-get` и `PGPASSWORD: coffee` в `environment`. ✅
