# Стандарт большой лабы и процесс написания

> Перенесено 20.10.2026 из `plan/README.md` (файл и папка `plan/` удалены: все лабы цепочки, кроме Ansible, написаны). Планы отдельных лаб лежат в папках самих лаб (`<лаба>/<лаба>_lab_plan.md`). Порядок прохождения и зависимости — `_order.md`; чек-лист интеграции — `_checklist-new-lab.md`; стандарт «схемы + настоящие результаты» — `_plan-schemes-results.md`; единые версии — `site.md`, раздел «Единые версии»; журнал — `_state-log.md`. История создания (кто, когда, что) — в журнале, здесь её нет.

## Правило 1: каждая лаба — либо самостоятельная, либо продолжение

```
bash  (самостоятельная)
docker ──▶ ansible          (Ansible разворачивает образ из Docker-лабы; написать осталось его)
docker ──▶ traefik ──▶ kubernetes
postgresql ──▶ prisma ──▶ express / nestjs / graphql (Prisma — «знания» PostgreSQL, ссылки в Express/NestJS/GraphQL)
```

**Как это работает без жёстких зависимостей.** У лаб цепочки DevOps есть **`starter/`** — готовый результат предыдущей лабы (исходники приложения, `compose.yaml`; образы собираются одной командой). У каждой два режима прохождения, оба описаны в её сессии 1:

- **«С нуля»** — берёшь `starter/` и идёшь по методичке; предыдущую лабу проходить не нужно.
- **«Продолжение»** — берёшь **свой** результат предыдущей лабы и продолжаешь с него; шаг «проверка стартового состояния» в сессии 1 подтверждает, что всё на месте.

`starter/` **не лежит в репозиториях**: его собирает читатель по методичке (Docker — шаг 11.5, Traefik — шаг 10.5). Решения владельца 13.10 и 20.10: не класть и не выносить архивы на Яндекс. **Исключение — Prisma Lab:** единственный стартовый файл (дамп базы `rental-legacy.dump`) лежит в её репозитории и раздаётся из бакета `prisma/rental-legacy.dump` (`tools/sync-bucket.py`).

**Сквозные проекты:** цепочка DevOps — **CoffeeShop** (Node.js API + frontend + PostgreSQL + Adminer), один на всех; у Bash — CoffeeOps (скрипты обслуживания); у Prisma Lab — «Прокат снаряжения» (RentKit).

## Правило 2: стандарт подробности («каждое слово объяснено»)

Образец — Caddy Lab и замечания владельца по её прохождению («не понятно, где и какие файлы создавать», «не знаю, что такое WebSocket/SSE», «шаг искали больше часа»). Каждая лаба содержит:

**Теория перед практикой (сессия 1):** «азбука» — что за предмет, какую проблему решает, как устроено, простыми словами и с аналогией; ничего не предполагается известным.

**У каждого шага:**
1. **«Слова шага»** — каждый новый термин: что это, зачем, аналогия, 1–2 строки; плюс врезка «Если совсем просто».
2. **«Где мы и что должно быть»** — какие файлы создать/изменить, что должно быть запущено. Не «добавь блок», а «вставь внутрь такого-то блока» / файл целиком.
3. **Команда разобрана по частям** — каждый флаг; вывод — построчно.
4. **«Как ещё можно»** — альтернативные пути.
5. **«Если не получилось»** — типичные ошибки с точным текстом сообщения, причиной и лечением; диагностика сверху вниз.
6. **«Под капотом»**, «Проверь себя» (2–3 вопроса), в конце сессии — «🔨 Сломать → починить».

**Бюджет шага (решение владельца 11.10.2026: «не растягивать сильно»).** По Caddy: в среднем ≈ 2 тыс. знаков на шаг (медиана ≈ 1,7 тыс., 90 % шагов до ≈ 2,9 тыс.; больше — только когда много кода). «Слова шага» — 3–6 терминов; «Как ещё можно», «Под капотом» и длинные разборы — в сворачиваемых блоках (`deep`); «Если не получилось» — только реально вероятные ошибки (2–4). Шаг заметно длиннее ≈ 3 тыс. знаков без большого кода — повод его разбить.

**У каждой сессии:** критерий приёмки («команда → ожидаемый вывод»), «Слова сессии», шаг 🔨 (сломать → починить), «Production Hell» без подсказок раз в 2–3 сессии. **Схема и аналогия** на ключевые места каждой содержательной сессии.

**В конце лабы:** справка — «симптом → причина → что делать», шпаргалка команд, глоссарий, вопросы для собеседования, «что дальше»; **последняя сессия — итоговое ТЗ без ответа** с таблицей приёмки.

## Правило 3: размер и устройство

- **Не меньше 10 сессий** по ~4 часа (время ориентировочное; после прохождения в подписи сессии ставится «автор за ≈ N ч»), 6–8 шагов на сессию; формат — как `caddy.html` (без инлайн-стилей, `quiz`/`links`/`outro`).
- Методички собираются **из Markdown-исходников** (`<лаба>/src/*.md`) генератором `tools/build-manual.py` (`--run` выполняет блоки в Docker и подставляет настоящий вывод; `--check` — только структура; `--allow-missing` — собрать без вывода, с пометкой «вывод не получен»). Править бандл вручную (`bundle.py`) — только мелкие правки.
- Версии-стандарт — `site.md` («Единые версии»); всё, что вне стандарта, помечается **«сверьтесь»** на момент написания.

## Правило 4: честность проверки

Каждая лаба при написании **проверяется запуском** (сухой прогон «как студент» в Docker/kind); если не проверялась — в «Ожидаемом результате» стоит пометка «вывод не получен», на сайте — статус «не вычитана и не проверена запуском», а список сомнительных мест лежит в `fixes/<направление>/<лаба>.md`. Тяжёлые прогоны — с предупреждением (ноутбук греется); Docker Desktop запускается **только с согласия владельца**, после работы убирается только созданное. Секреты (токены, ключи, пароли) **никогда не лежат в файлах репозитория**.

## Процесс написания

Каждый пункт закрывает проблему, которая уже случалась:

| Проблема из прошлого | Что закрывает |
|---|---|
| Готовые лабы «маленькие, почти ничего не рассказывается» | стандарт подробности + проверка структуры (`build-manual.py --check`, `audit_manuals.py`) |
| «Не понятно, где и какие файлы создавать» | блок «Где мы и что должно быть»; сухой прогон «как студент» до владельца |
| Вычитка другой моделью (Go Start/Go Pro) не принята | статус «принята» ставит **только владелец** |
| `jsub` правил скрытый текст, битый JSON ломал страницу | генератор из исходников вместо ручной правки бандла; проверка видимого текста в Chromium |
| «Проверено» на стендах, отличавшихся от студенческих | прогон только по тексту методички в чистой среде; отличия — `_dryrun-assumptions.md` |
| Ошибки в данных/версиях, которых не видно по тексту (Prisma: 2 двойные брони вместо 150; `ANALYZE` после восстановления) | сверка чисел и поведения **запуском**, прежде чем писать числа в тексте |

1. **Инструмент:** исходники `src/*.md` → `window.LAB` → `<ключ>.html` (в общем шаблоне) с проверкой JSON; сессию можно писать и править отдельным файлом.
2. **Проверка структуры:** у шага есть «Слова», «Если не получилось», «Проверь себя»; у сессии — приёмка и 🔨; у лабы — справка, глоссарий, вопросы; `check-site.py` ловит расхождения реестров.
3. **Пилот, потом партии:** одна сессия полностью — на утверждение стиля, затем партии по 3–4 сессии; перед партией сверка «состояние проекта на конец прошлой сессии».
4. **Сухой прогон «как студент»:** чистая папка/контейнер, только команды из методички; всё, где пришлось «догадаться», — находка в `fixes/`; окружение записывается.
5. **Вычитка отдельным проходом:** построчно, сверка кода между шагами, ссылки «раздел N / сессия N», видимый текст в Chromium.
6. **Статусы** (`_verification.md`, `_proofread.md`): `⬜` написана, не проверена → `🟡` проверена частично → `✅` вычитана и проверена ассистентом (с честным перечнем непроверенного); прохождение владельцем — отдельный, более высокий уровень; правки по её замечаниям идут через `docs/change_lab.md` (как в Caddy).
7. **«Готово»:** сессии собраны генератором; структура зелёная; сухой прогон по всем шагам, находки закрыты; справка, глоссарий, вопросы; `check-site.py` OK; интеграция по `_checklist-new-lab.md` (включая **страницу лабы** `works/<ключ>.html`, а не только методичку — урок 18.10).

**Правила очерёдности:** лаба N+1 не пишется целиком, пока у N нет проверенного `starter/`; правки Caddy-методички по замечаниям владельца имеют приоритет над новыми лабами; порядок и темп определяет владелец (по её команде, а не по расписанию).

## Решения владельца (11.10.2026 и позже)

1. Размер большой цепочки (~216 ч) — подходит; репозитории `bash-lab` и `ansible-lab` нужны (созданы 11.10).
2. **Swarm** остаётся внутри Docker и сжат до одной сессии (Docker 11 в плане; в написанной лабе Swarm не вошёл).
3. **VM-путь** (Vagrant/VirtualBox/Multipass/Lima) — необязательный вариант в сессии 9 Ansible; основной стенд — контейнеры с `sshd`.
4. **Calico** для `NetworkPolicy` в kind — запасной вариант в шаге 9.5 Kubernetes (по ходу выяснилось, что `kindnet` политики умеет применять; проверка — прогоном).
5. **Как пишутся лабы:** ассистент пишет сам, прямо в репозитории (исходники + генератор); исключение — Centrifugo (собрана отдельным чатом).
6. **Порядок цепочки:** Bash → Docker → Traefik → Kubernetes → Ansible (Ansible последней: боковая ветка, нужна меньше всего для типовой работы Laravel-разработчика); время сессий — ~4 ч как ориентир.
7. **Prisma 7, не 8** (20.10.2026); Prisma Lab после PostgreSQL и до Express/NestJS; единственный `starter/` — дамп базы, раздаётся из бакета.
