## 🧪 Сухой прогон 03.10.2026 (Docker Desktop 29.5.3, node:24-slim, postgres:18-alpine)
Прогнаны сессии 1–3 (кроме «Production Hell» 3.4 — она сломана намеренно, не проверялась). Образ, `.dockerignore`, три версии `entrypoint.sh`, том `pgdata`, сеть `lab-net`, ожидание БД, multi-stage, Compose с healthcheck, `.env`, лимиты (`mem=19MiB / 256MiB`) — работают.

- **[тех] Шаг 2.4: утверждение «node получил SIGTERM напрямую, остановился быстро» неверно.** Проверено: при `exec "$@"` контейнер **остаётся жив** после `docker kill -s TERM`, потому что у PID 1 в контейнере нет обработчиков сигналов по умолчанию, а в `server.js` его не было. Exec сам по себе ничего не даёт — приложение должно обработать SIGTERM. После добавления в `server.js` `process.on('SIGTERM', () => server.close(() => process.exit(0)))`: с `exec` — останавливается, без `exec` (bash PID 1) — остаётся жив, с `trap` — останавливается. ✅ обработчик добавлен в `server.js` (шаг 1.1), проверка в шаге 2.4 заменена на `docker kill -s TERM … && docker ps`.
- **[тех] Шаг 2.4: «без exec остановка займёт ~10 секунд» не воспроизводится** на Docker Desktop 29.5.3: `docker stop` занимает ~1,1 с и для `exec`, и для «глухого» PID 1 (даже для `alpine sleep 1000`). Замер времени ненадёжен → в методичке оставлено пояснение, проверка через состояние после SIGTERM. ✅
- **[тех] Шаг 1.4: `ps aux` внутри контейнера — `ps: command not found`** (в `node:*-slim` нет procps). ✅ заменено на `cat /proc/1/cmdline | tr '\0' ' '`.
- Подтверждено: PostgreSQL 18 хранит данные в `/var/lib/postgresql/18/docker`, том монтируется в `/var/lib/postgresql` (без `/data`) — данные переживают пересоздание контейнера.

- ✅ **«Production Hell» (3.4) прогнан (03.10, вечер):** сломанный compose ведёт себя как описано в разборе (порт `3000:8080` → пусто, `DB_HOST=postgresql` → приложение крутит «ещё не готов», `db` падает), и после исправлений всё работает (`db healthy`, `curl :3000` → «Привет!…»). **Шестая ошибка, которой не было в разборе:** без `.env` `POSTGRES_PASSWORD` пустой и контейнер `db` сразу падает (`Database is uninitialized and superuser password is not specified`) — добавлен пункт в разбор.
