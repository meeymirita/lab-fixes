Выводы `docker pull` очищены от промежуточных стадий («Pulling fs layer», «Download complete»): в терминале они не видны.

**Что найдено при прогоне и исправлено (классы ошибок, которые нельзя было увидеть без запуска):**
- Docker 29: у `docker inspect` пропало поле `.NetworkSettings.IPAddress` (теперь `.NetworkSettings.Networks.bridge.IPAddress`) — шаги 6.1, 10.2.
- Docker 29: сообщение «демон не запущен» теперь `failed to connect to the docker API at …` (раньше `Cannot connect to the Docker daemon …`); `docker images` печатает колонки `DISK USAGE`/`CONTENT SIZE`/`EXTRA`; `docker pull` без терминала печатает все стадии.
- Имя контейнера — не короче 2 символов (`--name a` не работает).
- BuildKit передаёт демону только нужные для `COPY` файлы и сжимает нули: демонстрация «контекст на 50 МБ» работает только с `COPY . .` и случайными данными (`/dev/urandom`) — шаг 4.4.
- `tmpfs` переживает `docker restart`, если главный процесс заново пишет файл: демонстрация переписана через отдельный `docker exec` — шаг 7.4.
- В `node:24-alpine` `npm` с зависимостями содержит 8 HIGH-уязвимостей (Trivy): сравнение с distroless-образом стало главным аргументом шага 5.5; у `nginx:1.30-alpine` — 3 HIGH, у `nginx-unprivileged` — 0 (шаг 11.1).
- `docker rm` без `-v` оставляет анонимные тома PostgreSQL: «осиротевшие» тома накапливаются уже с сессии 2; в тестовой среде удаляются `dangling=true`, на настоящем Mac — только по имени.
- PostgreSQL 18: монтирование тома в `/var/lib/postgresql/data` — контейнер завершается с понятным сообщением (шаг 7.7); `-v` с несуществующим файлом создаёт каталог → `psql … Is a directory`.
- `curl http://localhost:…` внутри инструментального контейнера не доходит до демона-«хоста»: curl разрешает `localhost` сам; в сборщике используется `~/.curlrc` с `connect-to = localhost::docker-dind:` (`CURL_HOME`); `-p 127.0.0.1:…`-порты из тестовой среды недоступны (`HTTP 000` у Adminer) — проверка заменена `docker compose exec adminer wget …`.

- YAML: `command: echo "…: …"` без кавычек — `mapping values are not allowed` (поймано в шаге 9.1 само, оставлено как «Если не получилось» с кавычками).

## 🧪 Сухой прогон 03.10.2026 (Docker Desktop 29.5.3, node:24-slim, postgres:18-alpine)
Прогнаны сессии 1–3 (кроме «Production Hell» 3.4 — она сломана намеренно, не проверялась). Образ, `.dockerignore`, три версии `entrypoint.sh`, том `pgdata`, сеть `lab-net`, ожидание БД, multi-stage, Compose с healthcheck, `.env`, лимиты (`mem=19MiB / 256MiB`) — работают.

- **[тех] Шаг 2.4: утверждение «node получил SIGTERM напрямую, остановился быстро» неверно.** Проверено: при `exec "$@"` контейнер **остаётся жив** после `docker kill -s TERM`, потому что у PID 1 в контейнере нет обработчиков сигналов по умолчанию, а в `server.js` его не было. Exec сам по себе ничего не даёт — приложение должно обработать SIGTERM. После добавления в `server.js` `process.on('SIGTERM', () => server.close(() => process.exit(0)))`: с `exec` — останавливается, без `exec` (bash PID 1) — остаётся жив, с `trap` — останавливается. ✅ обработчик добавлен в `server.js` (шаг 1.1), проверка в шаге 2.4 заменена на `docker kill -s TERM … && docker ps`.
- **[тех] Шаг 2.4: «без exec остановка займёт ~10 секунд» не воспроизводится** на Docker Desktop 29.5.3: `docker stop` занимает ~1,1 с и для `exec`, и для «глухого» PID 1 (даже для `alpine sleep 1000`). Замер времени ненадёжен → в методичке оставлено пояснение, проверка через состояние после SIGTERM. ✅
- **[тех] Шаг 1.4: `ps aux` внутри контейнера — `ps: command not found`** (в `node:*-slim` нет procps). ✅ заменено на `cat /proc/1/cmdline | tr '\0' ' '`.
- Подтверждено: PostgreSQL 18 хранит данные в `/var/lib/postgresql/18/docker`, том монтируется в `/var/lib/postgresql` (без `/data`) — данные переживают пересоздание контейнера.

- ✅ **«Production Hell» (3.4) прогнан (03.10, вечер):** сломанный compose ведёт себя как описано в разборе (порт `3000:8080` → пусто, `DB_HOST=postgresql` → приложение крутит «ещё не готов», `db` падает), и после исправлений всё работает (`db healthy`, `curl :3000` → «Привет!…»). **Шестая ошибка, которой не было в разборе:** без `.env` `POSTGRES_PASSWORD` пустой и контейнер `db` сразу падает (`Database is uninitialized and superuser password is not specified`) — добавлен пункт в разбор.
