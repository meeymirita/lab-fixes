# Связность цепочки Чистый JS → Vue → TypeScript (фронтенд)

Порядок прохождения: Чистый JS (8) → Vue (9) → TypeScript (10). TypeScript-лаба в сессии 5 использует Vue.
Проверка стыков: всё, что лаба использует, объяснено в ней или в предыдущей; всё, что обещано/ожидается от предыдущей лабы, там действительно есть.
Теги: **[пробел]** — используется без объяснения раньше в цепочке; **[наследство]** — ожидается от предыдущей лабы то, чего она не даёт;
**[расхождение]** — одно и то же в двух лабах называется/работает по-разному (версии, API, структура, термины); **[дубль]** — тема подробно разобрана заново, хотя уже была.

## Стык JS → Vue

- **[дубль] (важно) Vue-лаба, раздел 3 «Реактивность под капотом» vs JS-лаба, шаг 7.3** — JS-лаба подробно строит `reactive()+effect()` на Proxy и сама пишет: «🔬 Под капотом: это буквально алгоритм @vue/reactivity, упрощённый. Настоящий Vue использует практически идентичную структуру: targetMap…» (JS, часть 6/7). Vue-лаба в разделе 3 заново, с нуля, объясняет тот же механизм (Proxy get/set-ловушки, карта зависимостей, батчинг через `nextTick`) — без единой ссылки на JS-лабу, хотя студент, прошедший JS-лабу, только что реализовал это руками под тем же названием → в раздел 3 Vue-лабы стоит добавить фразу вида «если вы делали JS Lab — это тот же алгоритм, что вы написали в шаге 7.3, только полный», иначе связь «фундамент → надстройка» не читается, несмотря на то что JS README прямо называет себя «общим фундаментом» для Vue.
- **[расхождение] Docker-модель запуска команд** — JS-лаба (и далее TypeScript-лаба) строят вообще все команды вокруг `docker compose exec dev <cmd>` (выделенный sandbox-контейнер `dev` для каждого действия — 16 и 37+ вхождений соответственно). Vue-лаба работает иначе: `docker compose up -d` поднимает сервисы разом, и почти все шаги — это curl/браузер к уже работающим `api`/`web`; `docker compose exec` встречается всего 3 раза во всей методичке, и не через сервис `dev`, а напрямую через `web` (для `npm run test:unit`). Переход между моделями нигде не проговорён — учащийся, привыкший «все команды через `exec dev`», в Vue-лабе может не понять, почему тут почти не нужен exec.
- **[расхождение] Смена тестового стека без комментария** — JS-лаба учит `node --test` (`assert.equal/deepEqual`, `t.mock.timers`, `t.mock.method`); Vue-лаба сразу переключается на Vitest + Vue Test Utils (`expect().toBe()`, `vi.mock`, `vi.useFakeTimers()`) — другое семейство ассершенов и моков. Нигде в Vue-лабе нет фразы уровня «раньше вы писали `assert.equal`, здесь то же самое, но `expect().toBe()`» — притом что для других тем (store, race condition, разделение слоёв) Vue-лаба такие мостики как раз строит.

### Что проверено и в порядке
- Все содержательные форвард-ссылки JS-лабы на Vue-лабу («race condition, аналогичная гонке запросов из Vue-лабы» — сессия 5.2; «тот же паттерн, что Pinia в Vue-лабе» — 8.2; «то же разделение слоёв, что в Vue-лабе (компонент/store/api)» — 8.3; «Сравните… с `v-for` и `:key` в Vue» — 8.2) сверены с реальным содержанием Vue-лабы (`requestNo` в `ticketsStore` — вопрос 1.5/3.1, `:key` в разделе 3) — везде ведут на реально существующий материал, не на пустое место.
- JS README честно формулирует связь как «мягкую»: «Полезно проходить до Vue Lab… это их общий фундамент» — не «обязательно», и Vue README со своей стороны требует только общий «уверенный JavaScript (ES6+, async/await, деструктуризация)», не называя JS-лабу как жёсткую предпосылку — формулировки не противоречат друг другу.
- Домен «тикеты» совпадает у JS и Vue-лаб намеренно и заявлено как совпадение домена, а не кода («код при этом полностью свой, без единой связи с тем репозиторием» — JS README) — заявление проверено: общих файлов/импортов между репозиториями нет.

## Стык Vue → TypeScript

- **[противоречие] (важно) Обещание Vue-лабы «переведите TicketCard и ticketsStore» не выполняется в TypeScript-лабе** — раздел 13 Vue-лабы «Что дальше» прямо предлагает следующий шаг: «TypeScript во Vue — `<script setup lang="ts">`, типизированные props/emits/store — переведите TicketCard и ticketsStore; ошибки контрактов ловятся до запуска». TypeScript-лаба (сессия 5.3) действительно показывает типизированные `defineProps`/`defineEmits`/store, но делает это не на Helpdesk-домене Vue-лабы, а на совершенно новом Warehouse-приложении (`StockTable.vue`, `MovementForm.vue`, `useStockStore`) — ни `TicketCard`, ни `ticketsStore` нигде не встречаются и не переносятся. Заявленное упражнение «переведите TicketCard и ticketsStore» негде выполнить внутри самой методички → либо убрать конкретные имена компонентов из раздела 13 Vue-лабы (заменить на общую формулировку «переведите один из ваших компонентов»), либо реально дать в TS-лабе шаг с портированием именно этих Vue-компонентов.
- **[пробел] `defineProps<{…}>()` введён без моста к уже изученному синтаксису** — во всей Vue-лабе `defineProps` показан только в объектном runtime-варианте (`defineProps({ ticket: { type: Object, required: true }, … })`, раздел 2.6/4.4); generic-синтаксис `defineProps<{…}>()` там не упоминается ни разу, даже как превью «в TS будет по-другому». TypeScript-лаба (шаг 5.3) сразу даёт `const props = defineProps<{ rows: readonly StockRow[]; highlight?: string }>()` с однострочным комментарием «generic-синтаксис, где типы — обычный TS», не проговаривая явно, что это замена именно того объектного стиля, который студент использовал во всей Vue-лабе → добавить в TS-лабу (5.3) фразу вида «вместо `defineProps({ type: Object, required: true, … })`, который вы писали в Vue-лабе, здесь просто TS-тип».
- **[расхождение] Флаги `npm create vue@latest` расходятся без объяснения** — Vue-лаба: `npm create vue@latest web -- --router --pinia --vitest`; TypeScript-лаба (5.3): `npm create vue@latest web -- --ts --pinia` (без `--router` и без `--vitest`). Из-за этого в TS-лабе у итогового Vue-приложения нет ни роутера, ни сконфигурированного Vitest для `web`-пакета — что логично для маленького Warehouse-виджета, но нигде не объяснено, и студент, ожидающий «ту же структуру, что в Vue-лабе», может решить, что что-то забыл.
- **[расхождение] Стиль API-слоя меняется на противоположный без комментария** — Vue-лаба: API-слой — это набор функций по ресурсам (`ticketsApi.list/get/...`) поверх `http.js` с классом `ApiError extends Error` (ошибки — через исключения). TypeScript-лаба (5.1): один generic-клиент `createClient(baseUrl)` → `request<R extends Route>(route, opts)`, вызываемый как `api('GET /stock', {...})`, а бизнес-ошибки возвращаются не исключением, а `Result`-объектом (`{ ok: false, error }`) из раздела 2. Оба подхода в своих лабах объяснены и корректны сами по себе, но переход от «объект с методами + try/catch» к «один generic-вызов + Result» — значимая смена архитектурного стиля API-слоя, которую ни одна из методичек не проговаривает как сознательный шаг вперёд.
- **[расхождение] Культура тестирования компонентов теряется в сессии 5 TS-лабы** — Vue-лаба посвящает тестам компонентов/composable/store/guard целую сессию 5.3 («Тесты: 4 слоя», Vitest + Vue Test Utils). TypeScript-лаба, несмотря на то что активно использует Vitest в остальных пакетах (18→19 тестов, `expectTypeOf`, `@ts-expect-error`), для `packages/web` тестов вообще не пишет — единственная проверка `StockTable`/`MovementForm`/store — это `vue-tsc --build` на три заранее подготовленные ошибки типов. Компонентные Vitest-тесты, которым была посвящена вся сессия 5 Vue-лабы, в TS-версии того же стека не встречаются ни разу.

### Что проверено и в порядке
- Стиль стора идентичен: `defineStore('stock', () => { const rows = ref(...); ...; return {...} })` в TS-лабе — тот же setup-синтаксис Pinia (state как `ref`, actions как функции, явный `return`), что и в `stores/tickets.js` Vue-лабы; различается только наличие типов у `ref<StockRow[]>`.
- `TypedEmitter.on(...)`, возвращающий функцию отписки, откомментирован прямо в TS-лабе как «отписка — как в Vue-лабе» (раздел 3, `TypedEmitter`) — сверено с `onMounted/onUnmounted` + `socket.off` в Vue-лабе (раздел 2.9/сессия 5.1), ссылка ведёт на реально аналогичный паттерн, а не на пустое место.
- README TypeScript-лабы формулирует зависимость от Vue корректно и без завышенных ожиданий: «Логично проходить после или параллельно с Vue-лабой (сессия 5 её использует)» — сессия 5 действительно последняя и действительно использует Vue (Composition API + `<script setup>`, Pinia), это не жёсткая, а «знаниевая» связь, что совпадает с графом зависимостей в `_order.md`.
- Composition API + `<script setup>` как стиль написания компонентов не расходится: обе лабы одинаково избегают Options API (Vue-лаба показывает его только для сравнения в теории, TS-лаба вообще не упоминает).

## Сквозное

- **[расхождение] Docker exec-паттерн расходится дважды в цепочке** — JS-лаба и TypeScript-лаба обе построены вокруг единого паттерна `docker compose exec dev <cmd>`, а Vue-лаба — на «сервисы работают в фоне, обращайтесь через curl/браузер». Из трёх лаб фронтенд-цепочки именно средняя (Vue) выбивается из общего для JS и TS паттерна, и этот скачок туда-обратно нигде не объяснён ни в одной из методичек.
- Версии Node не расходятся содержательно: все три лабы одинаково держатся на `node:22` / «Node 22+ (24 LTS тоже подходит)» — это уже отмечено как «устаревающая, но не ломающая» мелочь в `js.md`/`vue.md`/`typescript.md` по отдельности, здесь противоречий между лабами нет.
